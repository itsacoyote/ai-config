# Creating Pull Requests

Related skills: branch names → `branch-names`; commit messages → `git-commit`.
Open the PR with the `gh` CLI (`gh pr create`) — prefer `git`/`gh` over other GitHub
integrations whenever the CLI can do the job.

## Step 1 — Preflight (discovery)

Do this discovery before writing anything, in order:

1. **Convention docs.** Check the target repository's root for `CLAUDE.md`, `AGENTS.md`,
   `CONTRIBUTING.md`, `.github/CONTRIBUTING.md`, and `docs/CONTRIBUTING.md`. **Read the
   ones that exist** for any required PR process — base branch, labels, reviewers,
   linked-issue syntax, title rules. **If the project's process conflicts with this skill
   (e.g. a non-Conventional-Commits title), the project's process wins.**
2. **PR template**, by GitHub's precedence — first single file wins, case-insensitive
   name: `.github/PULL_REQUEST_TEMPLATE.md`, then `PULL_REQUEST_TEMPLATE.md` at the repo
   root, then `docs/PULL_REQUEST_TEMPLATE.md`. If none, look for a
   `PULL_REQUEST_TEMPLATE/` directory (in `.github/`, the root, or `docs/`) — multiple
   templates means **you pick the one that fits the change (or ask)**. If the project has
   no template at all, use the fallback template at the end of this skill.
3. **Readiness.** Confirm: the current branch (not detached), the base/target branch
   (the remote's default unless the project says otherwise), that the branch is pushed
   (`git push -u origin <branch>` if it has no upstream, plain `git push` if it's behind),
   and whether a PR already exists for the branch (`gh pr list --head <branch>`) — if one
   exists, **edit it instead of opening a duplicate**.

## Signing policy

Follow the host repository's signing and push policy. Never bypass signing requirements
to push or update a pull request. If commits must be signed and you cannot produce a
valid signature, stop before pushing or opening the PR and ask a human to sign.

## PR Titles

Use the [Conventional Commits](https://www.conventionalcommits.org/) format:

```
<type>(<scope>): <short description>
```

**Types:** `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `style`, `ci`
(same set as commits — the `git-commit` skill is canonical for the type list and rules).

Same rules as a commit subject: lowercase, imperative mood, no trailing period, no
`Co-Authored-By` trailers. Scope is optional — use it when the change is isolated to
a clear area.

PR-title specifics:

- **Single-commit PR:** the title matches or summarizes that commit
- **Multi-commit PR:** write a title that captures the overall change, not just the first commit

**Examples:**

```
feat(agents): add model assignments to all agent frontmatter
fix(auth): handle expired token on refresh
docs: update setup instructions for new env vars
```

## PR Body

Fill in the body scaffold found in Step 1 — the project's template if one exists,
otherwise the fallback template below.

- Write as a human engineer would — clear, direct, and professional.
- **No AI attribution of any kind:** no "Generated by", "Co-authored by AI", robot
  emoji, or any mention of the AI tool that produced the change. It must read as if
  the engineer who built it wrote it themselves. (Same rule as `git-commit`.)
- Don't list every file changed — reviewers can read the diff.
- Keep it high-level enough that a human can understand what happened; add detail
  only where the change is complex or important.

## Fallback template

Use only when the project defines no PR template:

```markdown
## Description

- What was added/modified
- Why the change was necessary
- Any technical details worth noting

## Impact

- **UX**: How it affects user experience
- **Performance**: Any performance implications
- **Security**: Security-related impacts
- **Maintenance**: Effects on code maintainability

## Additional Information

<!-- Include any supplementary information, setup instructions,
or context that reviewers should know. -->

## Issues

<!-- Document any known issues, limitations, or pending concerns. -->

## Demo

<!-- Include relevant screenshots, GIFs, or video links demonstrating the changes. -->
```
